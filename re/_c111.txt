## And the gate was GREEN BEFORE AND AFTER, which is the finding

**THE GATE RUNS `g_acceptance`, `g_coverage`, `g_gap_compensation` and `g_rules`, AND NONE OF THE ELEVEN IS AMONG THEM.** So the repair cannot be caught by the gate --
**and that says something about the gate rather than about the repair**: **it checks the RULES and the SHAPES, and it does not cross-check the tools a layout claim was
derived from.** Dozens of scripts have been reporting class layouts that skipped offsets 1 to 9, `re/ledger.json` holds 468 claims, **and nothing connected the two.**

**THE CLAIMS THEMSELVES ARE NOT WITHDRAWN BY THIS -- AND THEY ARE NOT VINDICATED EITHER.** A claim whose witness is an instruction address in the module is unaffected by
which script found the address; **a claim whose witness is a line of a script's OUTPUT is now suspect**, and `re/ledger.json` does not record which tool produced a witness.
**That gap is the honest finding of this round**, and it is recorded rather than papered over: **the ledger grades the KIND of witness and not its PROVENANCE.**

**AND THE REPAIR'S OWN FIRST VERSION WAS WRONG THE SAME WAY.** It used `str.replace` to find a REGEX SOURCE inside a Python string literal, so its search string held one
backslash where the file holds two, **and it reported "no optional-displacement group found" for all fourteen targets while the scan had just found that group in
twenty-one lines.** **Substituting a regex's source text is `re.sub`'s job and not `str.replace`'s** -- and a tool that reports zero matches immediately after another tool
reported many is reporting its own bug.
