lcns: the nester family's TWO LAYERS are mapped from typeinfo -- and the sizes do not add up, which is recorded rather than papered over

**THE QUESTION THIS ROUND ASKED WAS WHETHER `LimitedNester`'S MISSING MIDDLE CLASS IS ONE INSTANCE OR A FAMILY-WIDE PATTERN. It is family-wide, and the typeinfo answers which
class each one derives from -- by reading the base pointer that `__si_class_type_info` carries at +0x10:**

    LimitedNester      vtable 0xA3B660   base N5Multi15CompositeNesterE
    FlipNester         vtable 0xA3B4A0   base N5Multi15CompositeNesterE
    MultiTorchNester   vtable 0xA3B8B0   base N5Multi15CompositeNesterE
    FilterNester       vtable 0xA3B500   base N5Multi15CompositeNesterE
    NestingNester      vtable 0xA3B6A0   base N5Multi6NesterE
    DatabaseNester     vtable 0xA3B750   base N5Multi6NesterE

**AND ALL FOUR OF THE FIRST GROUP DECLARE `public Nester`** -- so all four put every field 0x10 too low, exactly as `LimitedNester` did, **and `lcns/include/lcns/base_chain.hpp`
had already recorded the split** in the words *"TWO LAYERS, AND THE MIDDLE ONE WAS ENTIRELY MISSING"*. **The information was in the repository and four declarations beside it
disagreed with it.**

## And then the arithmetic refused to allow the fix, which is the more useful result

**THE MODULE ALLOCATES 0x28 BYTES FOR `FlipNester` AND `MultiTorchNester`:**

    02C953  mov ecx, 0x28          ; FlipNester
    02C958  call 0x998500          ; allocate
    02C96C  call 0x4B570           ; its constructor
    02C591  mov ecx, 0x28          ; MultiTorchNester, and 0x780E0 for its constructor

**and the model's objects would be 0x30**: `Nester` is 0x18 (a vptr and three fields, all written by 0xB4470), `CompositeNester` adds an 0x18 `std::vector`, and
`FlipNester` adds two bytes. **0x30 does not fit in 0x28.** So declaring the inheritance makes the model's class **larger than the module allocates** -- which is wrong in the
opposite direction from the 0x10-too-low it fixes.

**SO THE FOUR DECLARATIONS WERE REVERTED, AND THE CONTRADICTION IS RECORDED INSTEAD OF RESOLVED BY PREFERENCE.** One of these is true and this round does not know which:

  * **`Nester`'s base part is 0x10 and not 0x18**, so `0xB4470`'s two dwords at +0x10 and +0x14 belong to `CompositeNester`; or
  * **`CompositeNester` does not hold a `std::vector`**, and its 0x18 is something smaller; or
  * **`0x28` is not the object size** -- it is what the allocation site passes, and the class may be smaller than the block.

**AND THE SUITE COULD NOT HAVE TOLD ME EITHER WAY, WHICH IS THE ROUND'S SHARPEST FINDING**: `lcns/tests/test_recovered.cpp` asserts
`CHECK(kFlipNesterBytes == 0x28)`, and `kFlipNesterBytes` is an `inline constexpr int` in engine.hpp holding the same 0x28. **The test compares a constant to itself and never
`sizeof`s the model** -- so it passed with `FlipNester` at 0x30, and it would pass with it at 0x08. **A size check that cannot fail is not a size check.**
