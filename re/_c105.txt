**THREE THINGS CAME OUT OF MAPPING EVERY ENGINE'S OBJECT ACCESS, AND ONE OF THEM IS A TOOL BUG THAT HAD BEEN READING EVERY FIELD BACKWARDS.**

## The mapper called stores "reads" and reads "stores"

Its first version asked whether the instruction's TEXT matched `mov <size> ptr [..]` and treated everything else as a load -- **so `755298 mov dword ptr [r13], 0` came out
as a READ and `75545E mov qword ptr [r15 + 0x20], rax` came out as a WRITE.** A store places a field and a load only uses one, **and the objective asks for the
instruction that PUTS a member there**, so the two cannot be swapped. **The test is now the OPERAND'S POSITION** -- a memory operand before the comma is a destination
-- **and every offset in the report changed kind when it was fixed.**

## And the register with the most accesses is not the object in the two big engines

**`re/g_arg_access.py` prints EVERY argument register rather than tracking one**, **because the tracking breaks when a function spills `rcx` and reloads it elsewhere** --
which is why `EquivalentEngine::run` and `CompositeEngine::run` had come out empty. **And printing all of them is what showed the trap:**

    759D1D  lea r12, [rsp + 0x120]     ; **r12 is a STACK BUFFER**
    759E12  lea rbp, [rax + 0xb0]      ; **rbp points INSIDE a heap object**
    75A769  lea r12, [rsi + 0x68]      ; and r12 is reused for something else

**so the two registers with 41 and 31 "fields" are not the object at all** -- **and the two functions report the SAME 31 offsets through `r12` in the same order**, which is
what reading the same stack local from the same source code looks like. **The object register for those two is still UNFOUND.**
