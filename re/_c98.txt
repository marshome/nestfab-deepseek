re: the member-support audit was BLIND TO OFFSET ZERO -- every constructor's vtable store, and the class it made look unsupported

**THE TOOL ASKED "does the paired function write anything on this object?" AND ANSWERED NO FOR ONE CLASS -- `TimerWinImplementation` -- WHILE ITS CONSTRUCTOR'S THIRD
INSTRUCTION IS THE VTABLE STORE.**

    5F47C6  mov ecx, 0x10          ; allocate 0x10
    5F47CB  call 0x998500
    5F47D5  mov rbx, rax           ; **the object is the ALLOCATION, and rbx holds it**
    5F47DF  mov qword ptr [rbx], rax   ; **+0x00, the vtable**
    5F4810  movsd qword ptr [rbx + 8], xmm0   ; +0x08, `baselineSeconds_`

**AND THE CAUSE WAS ONE LINE**: its access regex captured the displacement only when there WAS one --

    base, offset = match.group(1), match.group(2)
    if offset is None:
        continue                       # **so `[rbx]` was skipped, and `[rbx]` IS the vtable**

**so EVERY constructor's vtable store was invisible, and a class whose only object write is that store came out as touching nothing.** Eight of the rows in the
report also carried the wrong offsets because of it: `NestingContextPool` and `NoFitMapCanceller` read `+0xC +0x10 +0x18 +0x1A` and now read `+0x0 +0xC +0x10
+0x18` -- **their vtable stores had been dropped too, and only the class with NO other write made it visible.**

**AND A SECOND BLINDNESS SAT BEHIND THE FIRST**: the tool's `holds` set began as `{rcx}` only, **so the ALLOCATOR's return value was never the object** -- `mov rbx, rax`
did not put `rbx` in it and every store through `rbx` was counted as neither the object nor the block. **Both are fixed: a `call` now puts `rax` in `holds`, because
that is where the allocator returns the block it just made.**
